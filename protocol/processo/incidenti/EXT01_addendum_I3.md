## Assertions that exceed the available evidence

The original body must be read together with its rectification, but the rectification does not repair every overstatement. The creation hash should be `f9290bb`, with `c7b42da` identified as refactoring. The 11 October 22:00 entry is a commit time, not a verified run time. “Float32 aggregates” should be narrowed to float32 probabilities and mixed-precision computations. The 108-cell diagnostic is distinct from the original control's six sampled aggregate recalculations.

The record supports a Spark-associated discrepancy and a tolerance patch. It does not establish the first detector's identity, the first failure time, a complete run history, a day's lost work, the literal impossibility of independent verification without this patch, or the causal role of processor architecture. The preserved report should not be represented as a post-patch full-check log. The threshold's empirical margin for this report is not a validation of sensitivity to every meaningful data error.

“None of the numbers changed” is defensible for the correction commit's changed paths and later comparisons within tolerance, not as a universal audit of all manuscript versions. Similarly, later Spark numerical checks pass, but the pub2 report's overall result is not a pass: it records a prose-only discrepancy.

The broad role-permission contrast remains unverified without the contemporaneous role instructions. Observing a branch and merge establishes an action, not the rule that permitted it. The card's transferability recommendations should be labelled recommendations, not empirical guarantees.

## Alternative explanations and missing discriminating evidence

1. **The check may be testing computational consistency rather than literal data identity.** A1 includes semantic pairing and aggregate checks; a changed calculation with unchanged input bytes could fail it. Input hashes alone do not replace those checks. Preserve and compare input fingerprints, calculation code and execution configurations to distinguish data mutation from computational differences.
2. **Deterministic implementation differences remain possible.** Different math-library builds, compiler choices, vectorised logarithms or runtime dispatch could produce stable cross-environment differences without run-to-run nondeterminism. The card already mentions libraries, threads and reductions; what is missing is a controlled distinction between stable cross-environment differences and repeated-run variability, with paired environment captures and repetitions.
3. **Threshold acceptance does not demonstrate error-detection sensitivity.** A3's “node/origin swaps give order-one errors” is a qualitative rationale, not a proof that every relevant corruption exceeds `1e-7`. Small perturbations may fall below that threshold, and absolute-zero edge cases remain under `atol=0`. An analytic error budget or separately authorised validation would be needed to justify general adequacy. No mutation experiment was performed here.
4. **The successful run can differ from the failing one in more than tolerance.** Later reports use later code and campaigns; they do not isolate the patch as the sole cause of a recovered run. A same-input, same-version pre/post-check record would discriminate this possibility. This is a limitation, not evidence that the patch was ineffective.
5. **The causal narrative may compress several events.** A3/A8 document Spark; the extra Mac run is a recollection. The chronology can remain unresolved without either denying that run or merging its alleged symptom with Spark's measured value. The original failure log, operator record and run identifier would be discriminating evidence.
